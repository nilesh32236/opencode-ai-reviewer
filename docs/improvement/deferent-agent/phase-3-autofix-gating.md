# Phase 3 — Autofix with Question Gating + Real PR Body

> **Goal:** Insert a pre-fix gate that blocks `/fix` when there are unanswered `required: true` questions on the issue, and replace the current "copy-paste the issue body" PR body with a proper summary built from `fixResult.summary` and `fixResult.filesChanged`.

This phase addresses **Findings F-1, F-2, F-3 (fix side)** from the master plan and depends on Phase 2's `issue_questions` table.

---

## 1. Background — what's wrong today

### 1.1 `/fix` does not wait for answers

The `/fix` flow in both App and Action auto-generates an analysis plan if none exists, then **immediately** calls `engine.runFix`. There is no check for outstanding questions.

**App** — `app/src/handlers/commands.ts:313-343`:

```ts
// Auto-analyze if no implementation plan exists yet
if (!issueContext.includes('<!-- issue-analysis-plan -->')) {
  logger.info('No implementation plan found — running analyze first');
  const planMarkdown = await engine.runAnalyze(issueNumber, issueContext, undefined, tempDir);
  await gh.postOrUpdateComment(issueNumber, '<!-- issue-analysis-plan -->', planMarkdown);
  issueContext = await gh.gatherContext({ issueNumber });
}

// ... immediately proceeds to:
const fixResult = await engine.runFix({ ... });
```

**Action** — `action/src/fix.ts:184-227` follows the same pattern.

The analyze prompt asks the LLM to populate "❓ Questions / Decisions Needed from Maintainer" (`lib/src/prompts/builder.ts:523-524, 554-555`), but those questions are just text inside the plan comment. Nothing tracks whether they've been answered. The fix prompt (`lib/src/prompts/builder.ts:333-340`) merely *instructs* the LLM to "Pay special attention to Human Feedback / Maintainer Instructions" — but if the maintainer hasn't answered, the LLM just picks an option on its own.

The user's request: *"if it require user questions it should not start fixing it it should wait for user replay and then start fixing it and if there is no question then it can start fixing it"* — maps exactly to this gap.

### 1.2 The PR body is a copy-paste of the issue body

**App** — `app/src/handlers/commands.ts:375`:

```ts
const prTitle = `[Autofix] ${issue.title}`;
const prBody = `## Fixes #${issueNumber}\n\n${issue.body}\n\n---\n*Auto-generated by opencode-ai-reviewer*`;
```

**Action** — `action/src/fix.ts:254-256`:

```ts
const issue = await gh.getIssue(issueNumber);
const prTitle = `[Autofix] ${issue.title}`;
const prBody = `## Fixes #${issueNumber}\n\n${issue.body}\n\n---\n*Auto-generated by opencode-ai-reviewer*`;
```

Both paths copy-paste the issue body verbatim. The fix summary that the LLM writes to `.fix-summary.md` during `engine.runFix` (read at `lib/src/engine.ts:475-480` into `fixResult.summary`) is **discarded** — never inserted into the PR body. It's only used in the autofix loop's `<!-- autofix-applied -->` iteration comment (`app/src/handlers/autofix.ts:476`; `action/src/fix.ts:701`).

The user's request: *"when it fix and open a pr it copy and past issue description not write fix summery which we need to review and fix carefully"* — confirmed.

### 1.3 The fix prompt has the context, but the gate is missing

To be fair to the existing code, the fix prompt *does* include the full issue context (plan + comments) as markdown. So when `/fix` runs after the maintainer has answered, the LLM does see the answers. The problem is that nothing prevents `/fix` from running *before* the maintainer has answered. The gate is what's missing, not the context propagation.

## 2. Design — gate first, then fix with a real summary

### 2.1 High-level flow

When `/fix` is invoked on an issue:

1. **Ensure a plan exists.** If no `<!-- issue-analysis-plan -->` comment is present, run `handleAnalyzeCommand` first (same as today). This now also populates the `issue_questions` table (Phase 2).
2. **Check for open `required: true` questions.** Query `store.getOpenQuestions(repo, issueNumber)` and filter to `required === true`.
3. **Gate.** If any required questions are open:
   - Post a single consolidated comment listing them with `⏸️ Waiting for maintainer answers before I can proceed.`
   - Return without fixing.
4. **Proceed.** If no required questions are open (either because there were none, or because they've all been answered), proceed to `engine.runFix` as today.
5. **Build the PR body from `fixResult`.** The PR body uses `fixResult.summary`, `fixResult.filesChanged`, the structured plan, and a collapsed `<details>` block with the original issue body for context.

### 2.2 The gate comment

When the gate blocks, the comment looks like:

```markdown
<!-- autofix-waiting -->

⏸️ **Holding off on the fix.** I have ${count} open question(s) that need answers before I can proceed:

> **q1** (required): Should we use zod or yup for runtime validation?
> Context: Both are already in the dependency tree.

> **q2** (required): Do you want me to add tests in this PR or a follow-up?
> Context: Adding tests will roughly double the diff size.

Reply to this comment (or quote-reply each question) with your answers, then run `/fix` again to proceed.

If you want me to proceed with my best-guess defaults anyway, run `/fix --force`.
```

The `<!-- autofix-waiting -->` marker lets subsequent `/fix` invocations find and update this comment (rather than posting a new one each time).

### 2.3 The escape hatch

`/fix --force` bypasses the gate. The LLM picks defaults for any unanswered required questions, and the audit trail records that the gate was bypassed (and by whom). This is the user's "if there is no question then it can start fixing" path made explicit — except here, even if there are questions, the maintainer can override.

This addresses the user's concern: by default the system waits, but the maintainer always has the override.

### 2.4 The new PR body template

```markdown
## Fixes #${issueNumber}

## Summary

${fixResult.summary}

## Files Changed

${fixResult.filesChanged.map(f => `- \`${f}\``).join('\n')}

## Implementation Plan Followed

${plan.implementationPlan.map((step, i) => `${i + 1}. ${step}`).join('\n')}

${plan.questionsForMaintainer.length > 0 ? `## Maintainer Decisions

${answeredQuestions.map(q => `- **${q.questionId}:** ${q.question}\n  - **Answer:** ${q.answerText} _(by @${q.answeredBy})_`).join('\n')}
` : ''}${tokenUsage ? `## Token Usage

${tokenUsage}
` : ''}---

<details>
<summary>Original Issue</summary>

${issue.body}

</details>

---
*Auto-generated by opencode-ai-reviewer. Review the changes carefully before merging.*
```

Key points:

- The fix summary is the **primary** content of the PR body, not the issue body.
- Files changed are listed for quick scanning.
- The implementation plan is included so reviewers can verify each step was done.
- Maintainer decisions (Q&A) are included so reviewers can see what was decided and by whom.
- The original issue body is in a collapsed `<details>` block at the bottom for context, not as the main content.
- Token usage is included (Phase 6 cross-cutting recommendation #8) so maintainers can see how expensive the fix was.

### 2.5 The template builder

A new helper `lib/src/prompts/fix-pr-body.ts` exports `buildAutofixPRBody(input)`:

```ts
export function buildAutofixPRBody(input: {
  issueNumber: number;
  fixResult: FixResult;
  plan: AnalyzeResult;
  answeredQuestions: IssueQuestion[];
  issueBody: string;
  tokenUsage?: string;
}): string
```

This is a pure function — easy to unit-test, easy to render-preview.

### 2.6 Context propagation into the fix prompt

Today the fix prompt at `lib/src/prompts/builder.ts:300-353` includes the entire `contextMarkdown` (which is `gatherContext`'s output — issue body + all comments). After Phase 2, this includes the `<!-- issue-analysis-plan -->` comment and the `<!-- issue-questions -->` comment.

To make the LLM's job easier, the fix prompt should **also** receive the structured plan and the answered questions as explicit fields, not just as part of the markdown soup:

```ts
buildFixPrompt({
  context,                    // existing: full markdown context
  plan,                       // NEW: structured AnalyzeResult
  answeredQuestions,          // NEW: structured Q&A
  verificationErrors,         // existing: from prior failed iteration
  // ...
})
```

The prompt then has a dedicated section:

```markdown
## Implementation Plan (Structured)

${plan.implementationPlan.map((s, i) => `${i + 1}. ${s}`).join('\n')}

## Maintainer Decisions (Structured)

${answeredQuestions.map(q => `- **Q: ${q.question}**\n  **A:** ${q.answerText} (by @${q.answeredBy})`).join('\n')}
```

This is in addition to (not instead of) the existing markdown context. Belt and suspenders: the structured fields are easier for the LLM to follow, the markdown context preserves anything the structured fields miss.

### 2.7 The `--force` audit trail

When `/fix --force` is used, a row is written to a new `fix_overrides` table:

```sql
CREATE TABLE IF NOT EXISTS fix_overrides (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  repo TEXT NOT NULL,
  issue_number INTEGER NOT NULL,
  user TEXT NOT NULL,
  reason TEXT,                -- optional, from /fix --force reason="..."
  bypassed_questions INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

This lets maintainers audit who bypassed the gate and when.

### 3.4 `app/src/handlers/commands.ts` (MODIFY — the heart of the change)

Refactor `createAutofixPR` (lines 249-418) to insert the gate and use the new PR body. The new flow:

```ts
export async function createAutofixPR(gh, engine, store, issueNumber, config, options: { force?: boolean }) {
  const repo = `${gh.owner}/${gh.repo}`;
  let issueContext = await gh.gatherContext({ issueNumber });

  // Step 1: Ensure a plan exists
  if (!issueContext.includes('<!-- issue-analysis-plan -->')) {
    logger.info('No implementation plan found — running analyze first');
    await handleAnalyzeCommand(issueNumber, repo, getToken(), config);
    issueContext = await gh.gatherContext({ issueNumber });
  }

  // Step 2: Fetch the structured plan and questions
  const plan = await store.getCurrentAnalysisPlan(repo, issueNumber);
  const openQuestions = await store.getOpenQuestions(repo, issueNumber);
  const requiredOpenQuestions = openQuestions.filter(q => q.required);
  const answeredQuestions = await store.getAnsweredQuestions(repo, issueNumber);

  // Step 3: Gate (unless --force)
  if (!options.force && requiredOpenQuestions.length > 0) {
    const waitComment = renderWaitComment(requiredOpenQuestions);
    await gh.postOrUpdateComment(issueNumber, '<!-- autofix-waiting -->', waitComment);
    logger.info(`Holding off on fix — ${requiredOpenQuestions.length} open required question(s)`);
    return { status: 'waiting', openQuestions: requiredOpenQuestions };
  }

  // Step 3b: Remove any prior waiting comment if we're proceeding
  await gh.deleteCommentByMarker(issueNumber, '<!-- autofix-waiting -->');

  // Step 4: Run the fix
  const fixResult = await engine.runFix({
    context: issueContext,
    plan,
    answeredQuestions,
    workingDir: tempDir,
  });

  // Step 5: Build the PR body from fixResult
  const issue = await gh.getIssue(issueNumber);
  const prTitle = `[Autofix] ${issue.title}`;
  const prBody = buildAutofixPRBody({
    issueNumber,
    fixResult,
    plan,
    answeredQuestions,
    issueBody: issue.body,
    tokenUsage: fixResult.tokenUsage,
  });

  // Step 6: Push the branch and open the PR
  // ... (same as today)

  // Step 7: If --force was used, log the override
  if (options.force && requiredOpenQuestions.length > 0) {
    await store.logFixOverride({
      repo, issueNumber,
      user: options.triggeredBy,
      bypassedQuestions: requiredOpenQuestions.length,
    });
  }

  return { status: 'fixed', prUrl, fixResult };
}
```

And update `handleCommand` for the `fix` case to parse `--force`:

```ts
case 'fix': {
  const force = args.includes('--force');
  const triggeredBy = event.comment.user.login;
  // ...
  await createAutofixPR(gh, engine, store, issueNumber, config, { force, triggeredBy });
  break;
}
```

- **Scenario F:** `allowForceOverride: false` config + `--force` → gate blocks anyway, error comment posted.

## 7. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Gate is too aggressive — blocks fixes that the LLM could reasonably make | Medium | Medium | Only `required: true` questions block. The LLM is instructed (Phase 2) to mark questions `required: false` when it can pick a sensible default. `--force` is always available. |
| Gate is too lax — LLM marks everything `required: false` and the gate never blocks | Medium | Medium | The Phase 2 prompt explicitly says "mark `required: true` when the fix cannot proceed without an answer." Meta-review (Phase 6) can audit the ratio of required vs. non-required questions and flag if the LLM is under-marking. |
| Maintainer doesn't realize the gate is blocking | Low | High | The `<!-- autofix-waiting -->` comment is posted in the issue, mentions the maintainer if possible, and lists the open questions explicitly. The bot also re-posts the comment (updating the existing one) if `/fix` is re-run while questions are still open. |
| `fixResult.summary` is too short / unhelpful for the PR body | Medium | Medium | The fix prompt already asks for a multi-paragraph summary. If summaries are too short in practice, tighten the prompt in a follow-up. The PR body template gracefully handles short summaries. |
| `fixResult.filesChanged` is empty (LLM didn't list files) | Low | Low | Fall back to `git diff --name-only HEAD~1..HEAD` in the workspace to get the list of changed files. More reliable than the LLM's report. |
| Maintainer uses `--force` excessively, defeating the gate | Medium | Low | The `fix_overrides` audit trail makes this visible. Repo admins can set `fix.allowForceOverride: false` to disable `--force` entirely. |
| PR body template breaks on issues with very long bodies (10000+ chars) | Low | Low | GitHub truncates PR bodies at 65,536 chars. The `<details>` block keeps the issue body collapsed by default. Tested in §4.1. |
| Existing autofix PRs that were opened with the old body template look inconsistent with new ones | Low | Cosmetic | Acceptable. New PRs use the new template; old PRs are not retroactively updated. |

## 8. Open Questions

1. **Should non-required questions also be surfaced in the PR body?** Recommendation: yes, in the "Maintainer Decisions" section, marked as "(non-required, default picked by bot)" if they weren't answered. This gives reviewers visibility into the LLM's defaults.

2. **Should the gate check for answered-since-last-`/analyze` or just answered?** Recommendation: just answered. If the maintainer answered an old question and then re-ran `/analyze` (which supersedes the old questions), the new questions would block. That's correct behavior.

3. **Should `--force` require admin permission?** Recommendation: no, any maintainer can use it, but it's logged. Repo admins can disable it entirely via `fix.allowForceOverride: false`.

4. **Should the PR body include a "Review Checklist" for reviewers?** Recommendation: yes, as a follow-up in Phase 6. Something like:
   ```markdown
   ## Reviewer Checklist
   - [ ] The fix summary accurately describes the changes
   - [ ] The implementation plan was followed
   - [ ] Maintainer decisions are reflected in the code
   - [ ] Tests pass
   ```

5. **Should the PR body link back to the `<!-- issue-analysis-plan -->` and `<!-- issue-questions -->` comments?** Recommendation: yes, with permalinks. Helps reviewers navigate the issue thread.

6. **What happens if `/fix` is run on an issue with no analysis plan and `analyze.askQuestions: false`?** Recommendation: the plan is generated (without questions), the gate finds no open questions, the fix proceeds. This is the "no questions, just fix" path the user requested.
