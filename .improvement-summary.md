## Changes

### 1. Fixed a SQLite transaction concurrency bug (`lib/src/learning/db/sqlite.ts`)
`SqliteAdapter.transaction()` used manual `BEGIN TRANSACTION` / `COMMIT` / `ROLLBACK` with an `await fn()` between BEGIN and COMMIT. Because the `await` yields to the event loop, two concurrent callers on the single shared better-sqlite3 connection could interleave — the second `BEGIN TRANSACTION` would throw `cannot start a transaction within a transaction` or corrupt the BEGIN/COMMIT pairing. The Postgres/MySQL adapters already serialize via the promise-chain mutex `serializeTransaction()`; the SQLite adapter did not. Wrapped the SQLite transaction body in `serializeTransaction()` so all adapters share identical transaction semantics.

Also corrected the misleading comment in `lib/src/learning/db/sql-adapter.ts` that claimed better-sqlite3 was "unaffected" by concurrency.

### 2. Classified deterministic GraphQL errors as non-retryable (`lib/src/utils/github.ts`)
`graphql()` threw a bare `Error` for GraphQL application-level errors (e.g. `Could not resolve to a node`), which carry no HTTP status. `withRetry` treated those as status-0 "unknown/network" errors and retried them up to `maxRetries` times even though they are deterministic and will never recover. The error now carries `status: 422` (a non-retryable 4xx) so `withRetry` skips retries, while genuine HTTP-level 429/5xx responses still follow the normal retry policy. This avoids wasted retries and noisy warnings on deterministic failures.

### 3. Added regression tests
- `lib/tests/db-adapter.test.ts`: new test `serializes concurrent transactions so BEGIN/COMMIT never interleave` — runs two transactions concurrently via `Promise.all` and asserts both commit (this failed before the fix with an interleaved-BEGIN error).
- `lib/tests/github.test.ts`: new `graphql error classification` test asserting a GraphQL `errors` response rejects with `status: 422` and the prefixed message.
