## What I changed and why
**Problem:** HTTP status extraction was fragmented across three implementations:
`getErrorStatus()` (`lib/src/utils/errors.ts`) read only `err.status`,
`withRetry()` (`lib/src/utils/retry.ts`) used its own inline
`err instanceof Error && 'status' in err` check (blind to `Response` objects,
`statusCode`, axios-style `response.status`, and `cause` chains), and
`circuit-breaker.ts` had a third private copy (`getHttpStatus`). Consequence: a
deterministic 4xx surfaced as `statusCode`/`response.status` was misclassified
as status `0` (unknown) — retried wastefully instead of failing fast, and
counted toward tripping the circuit breaker.

1. `lib/src/utils/errors.ts` — `getErrorStatus()` now covers `status`,
   `statusCode`, `response.status`/`response.statusCode`, and bounded
   (depth-4, cycle-guarded) `cause` chains; `status` takes precedence; only
   finite numbers accepted (numeric strings still rejected); every property
   read is guarded so the helper truly never throws (previously a throwing
   getter propagated, contradicting its own docstring).
2. `lib/src/utils/retry.ts` — `withRetry()` uses `getErrorStatus(err) ?? 0`;
   added opt-in `onRetry` hook (`RetryAttemptInfo`: attempt, maxRetries,
   status, delayMs, error) for metrics/diagnostic logging; throwing hooks are
   contained via a warning and never break the retry loop. `withRetryAndTimeout`
   inherits both through option forwarding.
3. `lib/src/utils/circuit-breaker.ts` — removed duplicated `getHttpStatus`;
   `countHttpError()` now delegates to `getErrorStatus()`.
4. `lib/src/index.ts` — additive exports: `RetryOptions`, `RetryAttemptInfo`,
   `countHttpError`, `CircuitBreakerMetrics` (needed for consumers to type and
   use the new hook/classifier).
5. Rebuilt bundles via `pnpm build` (`action/lib/index.js`,
   `action/lib/post/index.js` regenerated).
